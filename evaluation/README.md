# 性能评价与复现

本目录包含独立的模拟数据实验。实验只在临时目录创建数据库，不打开、不修改运行中的 `database/localdeal.db`，也不会改变已有账号、点评、订单或核销记录。

## 2026-11-27 智能功能升级评价

- [新版分页及推荐评分报告](results/insights-pagination-2026-11-27/summary.md)：相同三档规模和 30 次重复测量，但纳入新版评分和解释字段。最大规模首页数据从 28.64 MiB 降至 13.24 KiB，组装与编码中位数由 339.94 ms 降至 27.25 ms。新推荐在分页前排序全部匹配候选，因此有额外成本；10 月 3 日的 2.79 ms 是历史编号排序结果，不代表当前实现。
- [事务并发报告](results/transactions-2026-11-27-125150/summary.md)：1、8、32 个线程，每档 5 次，每次 100 位模拟买家与 10 张库存。每次售出 10、售罄 90、忙等待失败 0，库存为 0，重复请求返回原订单。高并发增加写锁等待，不能声称 SQLite 吞吐随线程数线性增加。
- [新版分页图](results/insights-pagination-2026-11-27/pagination-comparison.png) · [事务实验图](results/transactions-2026-11-27-125150/transaction-contention.png)。复现：`python3 -B evaluation/transaction_benchmark.py`，`python3 -B evaluation/pagination_benchmark.py`。绘图可选用 `python3 -B evaluation/plot_results.py <results.json>`。

以下保留 10 月实验原始结果和当时实现背景。

## 原始索引对照（分页前）

2026-10-03 在本机完成三档规模、七个查询案例的 21 组索引对照。最大一档包含 20,000 个模拟用户、2,000 家模拟门店、100,000 条点评与 50,000 个订单。每个查询在两种索引条件下各测量 30 次，返回结果一致，外键、完整性、生成数量及库存与售出数检查通过。

| 最大规模中的案例 | 移除业务二级索引的中位耗时 | 保留业务二级索引的中位耗时 | 解读 |
| --- | ---: | ---: | --- |
| 普通门店最新 10 条点评 | 0.0210 ms | 0.0089 ms | 本次约 2.37 倍；该门店的点评数量约 45 条 |
| 热门门店最新 10 条点评 | 2.2833 ms | 0.0101 ms | 本次约 226 倍；这是拥有 10,000 条点评的刻意构造案例 |
| 商户授权门店订单 | 9.6941 ms | 0.3770 ms | 本次约 25.72 倍，返回相同 250 条订单 |
| 高频买家全部券包 | 6.7220 ms | 6.3284 ms | 改善很小；仍需取回 5,000 条订单 |
| 地区和类别发现页 | 18.0222 ms | 18.9902 ms | 本次没有改善，不应声称所有查询都被索引加速 |

这些是重复本机读取的中位数，不是 HTTP 响应时间、所有用户的平均值或承载能力。SQL 点评实验使用 `LIMIT 10`；原实验时接口尚未分页。基线仍保留主键及唯一约束需要的索引，不能称为“完全没有索引”。原始 JSON 与报告保留当时实现的说明，不代表分页后的接口。

原实验还测量了分页前 `service.state(None)` 的完整数据组装及 JSON 编码。最大一档返回全部 100,000 条点评，响应约 28.64 MiB，三次测量中位数约 349.11 ms；网络传输和浏览器渲染不在此时间内。原公开读取函数现保存为 `baseline_guest.py`，用于复现原始全量读取，不接入应用路由。

## 分页后的前后对照

发现页筛选现先在 SQL 中限定门店；初始化读取摘要与推荐卡片，门店、优惠、点评、个人列表与商户台账使用分页接口。以下在相同生成数据、相同业务索引及 JSON 编码范围内重新测量。每个首页条件暖身三次、随机交替测量 30 次；新首页统计初始化与首屏 12 家门店两个响应的总量。

| 模拟规模：门店 / 点评 / 订单 | 旧首页响应 | 新首页两个响应合计 | 旧组装＋编码中位耗时 | 新组装＋编码中位耗时 |
| --- | ---: | ---: | ---: | ---: |
| 100 / 5,000 / 2,000 | 1,459.78 KiB | 11.04 KiB | 14.20 ms | 0.40 ms |
| 1,000 / 50,000 / 20,000 | 14,654.09 KiB | 11.04 KiB | 159.32 ms | 1.58 ms |
| 2,000 / 100,000 / 50,000 | 29,324.30 KiB（28.64 MiB） | 11.04 KiB | 325.22 ms | 2.79 ms |

最大规模中，热门门店首 10 条点评为 4.19 KiB，组装与编码中位数 0.16 ms；高频买家首 10 笔订单为 4.07 KiB、1.97 ms；授权商户首 10 笔订单为 4.22 KiB、0.26 ms；地区/类别筛选首 12 家店为 9.39 KiB、1.34 ms。响应包含完整筛选数量，门店评分及点评数与旧实现一致。

这些是服务函数组装与编码时间，包含数量查询，排除 HTTP、网络、浏览器及登录耗时。首页对照限定访客；登录后的发现页还有收藏页和个人计数请求。商户案例未指定 `storeId`，统计全部授权门店的订单分页，未统计完整工作台及其分店详情请求。新旧首页返回范围发生变化，因此不声称全量响应完全相同；后续页、门店详情及本人完整导出仍可读取相应资料。热门门店仍包含刻意生成的 10% 点评；多次读取不是独立用户采样，也没有测量网站并发容量。

## 重新测量

当前分页前后对照，在项目根目录运行：

```sh
python3 -B evaluation/pagination_benchmark.py
```

复现原始索引对照（固定保留的全量查询及旧公开状态）：

```sh
python3 -B evaluation/benchmark.py
```

默认会生成三档规模，每个案例在两种条件下各测量 30 次。结果保存到以香港运行时间命名的新文件夹；已有实验结果不会被覆盖。新的耗时可能因电脑、缓存和系统负载变化，不能要求每次完全相同。

只做较小规模检查可以运行：

```sh
python3 -B evaluation/benchmark.py --scales small --repetitions 30
```

若安装了 Matplotlib，可把终端显示的实际结果目录替换到以下命令，重新生成图表：

```sh
python3 -B evaluation/plot_results.py evaluation/results/实际目录/results.json
```

## 公平比较及当前限制

两种条件从同一份生成数据复制而来，仅在实验副本中移除 13 个业务显式二级索引。主键、唯一约束、外键、检查约束、触发器和两个空会话表索引保留。两份数据库都进行 `ANALYZE`，使用相同页缓存和自动索引设置；暖身后随机交替计时。测量包含执行和取完结果，排除建库、连接建立和查询计划获取。

每个案例固定一个实体参数，重复测量不等于独立采样 30 个用户或门店。普通门店与普通买家的匹配记录数几乎固定，热门案例的匹配记录数才随规模增长。单机缓存读取、三次全量组装、人为偏斜和有限参数都限制了结论范围。

原发现页视图会先扫描、聚合全部门店及点评；当前页面已改用所选门店的限定查询，并按页返回。分页控制响应记录数；总数及平均评分仍需读取匹配的数据库记录，评分排序可能遍历全部匹配门店，较深的 OFFSET 也会增加成本。原始索引实验与分页服务实验的计时范围不同，不能把两者倍数相乘。索引的存储增加已记录，写入吞吐、并发负载、网络、网页渲染和公开部署尚未测量。

查询计划和索引解释参考 SQLite 官方的 [Query Planner](https://www.sqlite.org/queryplanner.html)、[EXPLAIN QUERY PLAN](https://www.sqlite.org/eqp.html) 与 [ANALYZE](https://www.sqlite.org/lang_analyze.html) 文档。
